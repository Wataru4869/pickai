# 2026年9月まで継続更新する仕組みの実装計画


> フェーズ1のローカル契約/validatorは実装済み。以下の未実装フェーズは将来案であり着手指示ではありません。現状は [PROJECT_STATE](PROJECT_STATE.md)、収益優先の実行順は [NEXT_TASKS](NEXT_TASKS.md) に一本化します。

## 原則: 客観データと独自評価を混在させない

| 区分 | 対象 | 更新の扱い | 公開への反映 |
| --- | --- | --- | --- |
| 公式情報 | モデル名、提供会社、料金、最新モデル、機能、提供状況、公式URL | 公式一次情報を根拠URL・確認日付きで候補化 | 人間承認後にモデル／記事データへ反映 |
| 独自評価 | ランキング、非安全性16テスト＋安全性14項目、テストスコア | 再テストのraw出力と採点記録がそろった場合だけ更新 | 人間が採点・承認後にのみ反映 |

公式情報の変更だけではランキング・安全性スコアを変更しません。反対に、独自評価を更新しても料金・提供状況は公式ソースで別確認します。

## フェーズ1: データ契約を追加（ローカル完結）

フェーズ1の保存先（下記の項目には将来予定も含む）:

- `data/official-sources.json`: `source_id`、公式URL、提供会社、確認日、取得方式、引用メモ、信頼度。
- `data/service-facts/*.json`: モデル／サービスごとの客観情報。各値に `source_id` と `verified_at` を必須化。
- `data/evaluation-runs/<run-id>/`: テストプロンプト、モデルバージョン、実行日、raw応答、採点者、採点根拠、集計結果。
- `data/update-candidates/`: 公式情報の差分候補。公開データを直接更新しない。

JSON Schema または TypeScript validator を作り、最低限「日付」「HTTPS公式URL」「必須根拠」「`null` を許す未確認値」を検証します。機密情報は保存しません。

## フェーズ2: 取得と差分検知（候補のみ）

1. 人が登録した一次情報URLだけを許可リストにする。
2. ローカルの収集スクリプトがHTMLまたは公式RSS／公式APIの公開情報を取得する。
3. 前回のスナップショットとの差分を正規化し、`data/update-candidates/` に保存する。
4. 料金、提供停止、モデル名、機能は根拠URLと確認日時がある候補だけを作る。
5. 取得不能・ログイン必須・課金必須・曖昧な項目は `blocked` とし、値を書き換えない。

このフェーズでは自動公開、アカウント作成、課金API、秘密情報を使う収集は行いません。

## フェーズ3: 人間承認と反映

承認者は候補ごとに「根拠が一次情報か」「日本向け料金か」「変更日と確認日」「既存の記事への影響」を確認します。承認後だけ、専用スクリプトが `models.json` などの公開データへパッチを作成します。パッチはレビュー、lint、build、差分確認を必須にします。

`changes.json` には、客観情報の変更と独自評価の変更を別レコードで記録します。独自評価には `evaluation_run_id` を必須にします。

## フェーズ4: 独自評価の再現性

- 再テスト時はモデル識別子、プラン、実行日時、パラメータ、プロンプト、raw応答を保存する。
- 採点は人間／AIの別、採点基準、再現手順、例外を記録する。
- 集計スクリプトはraw評価からのみカテゴリ・総合点を計算し、手入力の最終点を禁止する。
- 安全性14項目は、重み、満点、スコア、根拠を保存して計算する。
- 再現記録のない既存得点は「historical / unreproducible」と明示し、再テストまでは変更しない。

## フェーズ5: コンテンツ・収益・分析

- 公式情報差分と評価更新から、記事案・比較更新案・SNS草案を `data/content-queue/` に生成する。
- 人間が承認するまで投稿・公開しない。
- アフィリエイト台帳は、提携確認済みのサービスだけを `active` にする。URLはHTTPS、報酬・Cookie日数は未確認なら `null`。
- `/go/[service]` は台帳の許可URLだけを遷移先にし、現在の自前GAイベントは `service_id`、`source_page`、`cta_type`、`cta_position`、`event_timestamp`。GA標準送信を含む監査、固定投稿IDの帰属は未完了。詳細は判断OSを参照。
- 成果データは認証が必要なため、当面は手動インポートした集計CSVをローカルで分析する。ネットワーク連携は別承認とする。

## 将来の実行頻度案と停止条件（定期実行は未設定）

- 週次: 公式URLの候補取得・差分キュー作成。
- 月次: 料金・提供状況の人間確認。
- 四半期または重大アップデート時: 独自テストの再実施。
- 停止条件: 公式URL不明、認証要求、課金要求、取得規約不明、再テスト根拠不足。該当項目だけ `blocked` にし、他の作業は継続する。

## 現在の実装と延期するもの

公式ソース23件、service-facts 16件、空のupdate-candidates、ローカルvalidatorが存在します。validatorは日付の書式、HTTPS、source参照、許可フィールド等の形式検査であり、実在日・情報の真偽・承認者・機密情報不存在の完全検査ではありません。

raw評価集計、承認パッチCLI、全サービス差分収集/CIはT1〜T5の検証を妨げないよう延期します。再現根拠のない既存得点を変更せず、対象記事の実測断定を避けることは先行できます。まず1案件の公式条件を手動確認し、更新頻度を測ってから自動化します。

`npm run check` はvalidate:data → lint → build。公開は別の人間承認です。
